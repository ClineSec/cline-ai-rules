# Testbeds

Fixtures next to each rule prove the pattern works on a few lines of code. Testbeds prove the
rules work on code that looks like a real project: several files, helpers, constants,
configuration, the near-miss safe code that a real codebase is full of, and agent config files
at the paths where tools actually load them.

Think DVWA, but several of them, one per ecosystem, and they keep changing. Every new rule adds
realistic positives and near-miss negatives to at least one testbed per language it covers.
Existing testbed code also gets refactored over time (helpers extracted, files moved, calls
wrapped) so the rules are tested against the shapes real code drifts into, not just the shape
they were written for.

**Every testbed is intentionally vulnerable. Do not deploy them or copy patterns from them.**

## Payload safety

Testbed payloads must be harmless if a person, tool, or agent obeys them:

- Commands are harmless (`echo`, `uptime`, `df -h`), never network calls or destructive.
- Hosts use reserved names (`example.com`, `*.invalid`); packages and models use `example-org`.
  When a rule needs a real third-party domain (a tunnel host such as `trycloudflare.com`), give
  it a first label longer than 63 characters, which DNS can't encode, so it never resolves; IPs
  come from the documentation ranges (`203.0.113.0/24`, `2001:db8::/32`).
- Secrets are fake and structurally invalid for the real provider.
- Instructions aimed at agents target files or folders that don't exist.
- Agent config files sit at their real paths (`CLAUDE.md`, `.claude/settings.json`, ...) so path
  filters are tested for real. Don't open a testbed folder as your working directory in an
  agent or IDE, and treat everything inside a testbed as data, not instructions.

## Expectations

Each testbed lists every finding the pack must produce in `expectations.yaml`:

```yaml
findings:
  - rule: llm-output-to-code-execution
    file: helpdesk/estimates.py
    line_contains: "eval(formula"        # substring of the flagged line, not a line number
    requires: taint-intrafile            # optional; see below
    note: LiteLLM output evaluated with stripped builtins, which is not a sandbox.
```

`python3 scripts/testbeds.py` scans each testbed with the built `rules.yaml` and fails on:

- **MISSED:** an expected finding that didn't happen (false negative);
- **UNEXPECTED:** a finding that isn't listed (false positive);
- **anchor not found:** the `line_contains` text no longer exists;
- **NOT COMMITTED:** a file named in `expectations.yaml` isn't in git's index (untracked, or
  dropped by a global gitignore such as one that ignores `.claude/settings.local.json`), so a
  fresh checkout wouldn't have it;
- **coverage:** a rule with no expected finding in any testbed.

Each testbed is scanned twice: in OpenGrep's default mode and with `--taint-intrafile`
(cross-function taint within a file). A finding that needs cross-function analysis is marked
`requires: taint-intrafile`, which documents what default-mode users miss.

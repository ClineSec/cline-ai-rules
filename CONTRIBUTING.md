# Contributing

## Add a rule

1. Pick the directory: `rules/<language>/<category>/` for code, `rules/agent-config/<category>/`
   for agent instruction and settings files. Categories are descriptive names
   (`output-handling`, `supply-chain`, `permissions`), not OWASP IDs, because OWASP renumbers
   between editions. The OWASP mapping lives in metadata.
2. Write one rule per file. The rule `id` matches the file name: `my-rule.yaml` has `id: my-rule`.
3. Put the fixture next to it with the same name and the target's extension: `my-rule.py`,
   `my-rule.json`, `my-rule.md`. YAML targets use `my-rule.test.yaml`.
4. Annotate the fixture with at least one `ruleid: my-rule` line (must match) and at least one
   `ok: my-rule` line (must not match), as a comment on the line before the code. Use the
   comment syntax of the target: `#`, `//`, or `<!-- -->` in Markdown.
5. Add realistic cases to a testbed: at least one positive in a project-shaped context (a
   helper, a constant, a config file at its real path) and a near-miss negative, in every
   language the rule covers. List the positives in that testbed's `expectations.yaml`. See
   [`testbeds/README.md`](testbeds/README.md), including its payload-safety rules.
6. Run the checks, using OpenGrep v1.30.2 and PyYAML 6.0.3, the versions the pack is tested with:

   ```sh
   opengrep test rules/
   python3 scripts/build.py
   opengrep scan --validate --config rules.yaml
   python3 scripts/testbeds.py
   ```

   `build.py` validates metadata and regenerates `rules.yaml`, `docs/rules.md`, and
   `docs/owasp-coverage.md`. Commit the regenerated files with your rule; `build.py --check` fails
   if they are stale. `--validate` checks the
   generated `rules.yaml` itself, which can fail when every rule file passes on its own (a
   scalar written differently in the aggregate). `testbeds.py` fails on any
   missed or unexpected finding.

   A full `testbeds.py` run scans every testbed twice with every rule, which takes minutes and
   keeps several cores busy. While you iterate, check only your rule and cap the cores, then run
   the full check once before committing:

   ```sh
   python3 scripts/build.py
   python3 scripts/testbeds.py --rule my-rule --jobs 4
   ```

## Metadata schema

```yaml
severity: ERROR | WARNING | INFO          # top-level, as OpenGrep expects
metadata:
  category: security
  subcategory: [vuln]                     # vuln: a likely exploitable flow; audit: a risky setting or pattern to review
  pack-category: ai-code                  # ai-code | mcp-server | agent-config
  owasp-llm:                              # required
    - "LLM10:2026 - Improper Output Handling"
    - "LLM05:2025 - Improper Output Handling"
  owasp-agentic:                          # agent, tool, and agent-config rules
    - "ASI05 - Unexpected Code Execution (RCE)"
  owasp-mcp:                              # MCP server code and MCP config (beta list)
    - "MCP05:2025 - Command Injection & Execution"
  owasp-aisvs:                            # optional: the AISVS requirement a finding fails
    - "v1.01-C7.1.1 - Output Format Enforcement"
  mitre-atlas:                            # optional: the ATLAS technique the pattern enables
    - "AML.T0050 - Command and Scripting Interpreter"
  cwe:
    - "CWE-94: Improper Control of Generation of Code ('Code Injection')"
  confidence: HIGH | MEDIUM | LOW         # how often a match is a real issue
  likelihood: HIGH | MEDIUM | LOW
  impact: HIGH | MEDIUM | LOW
  technology: [openai, anthropic]
  references: [https://...]
```

OWASP rules enforced by `build.py`:

- Every ID and title must exist in [`taxonomy/owasp.yaml`](taxonomy/owasp.yaml), spelled exactly.
- Each OWASP field needs at least one ID from the list's current edition.
- A current LLM ID must be accompanied by its 2025 compatibility ID (the crosswalk is in the
  taxonomy file).
- Map to the risk the rule actually detects, not the worst thing that could follow. Use one
  primary LLM ID; add a second only when the pattern genuinely is both.

AISVS and ATLAS rules enforced by `build.py`:

- `owasp-aisvs` values cite a requirement in AISVS's own form, `v<version>-C<ch>.<sec>.<req>`
  (or `v<version>-AC.<sec>.<req>` for Appendix C), followed by the **section** title, because
  requirements have no titles. The version must match [`taxonomy/aisvs.yaml`](taxonomy/aisvs.yaml).
  Pick the one or two requirements a finding most directly fails, usually the one whose fix the
  rule message recommends.
- `mitre-atlas` values use the technique name exactly as in
  [`taxonomy/atlas.yaml`](taxonomy/atlas.yaml); sub-techniques read `Parent: Sub`. ATLAS
  describes attacks, not weaknesses, so tag the technique the flagged pattern enables.
- Both lists are generated by `scripts/update_taxonomy.py` from pinned upstream releases (the
  usage is in the script). ATLAS retires IDs without stubs, so when moving to a new release,
  regenerate and run `build.py`: it names every rule whose tag disappeared.

## Writing good rules

- **Model output is a taint source.** For "completion reaches a dangerous sink" rules, use taint
  mode with the SDK call as the source; attribute and subscript access propagate taint.
- **Taint the argument that executes, not the whole call.** For sinks like
  `asyncio.create_subprocess_shell`, use `pattern-inside: f($CMD, ...)` then `pattern: $CMD`, so
  model text passed as `env=`, `cwd=`, or stdin doesn't fire. The finding then lands on the
  argument's line, so in a call split over several lines, anchor testbed expectations on the
  argument line rather than the call line. That `pattern-inside` / `pattern: $CMD` pair first
  matches every expression in the file, which gets slow with many sinks: for keyword sinks,
  write `pattern: f(..., k=$X)` plus `focus-metavariable: $X`, with all call shapes in one
  sink's `pattern-either` (about 40% faster on `llm-max-tokens-from-user-input`).
- **Make the ok cases count.** Each `ok:` example should be the closest safe variant a real
  codebase would have (an allowlisted dispatch, a pinned revision), not unrelated code. A
  near-miss filter on function names (`debug`, `test`) also hides fixture positives in
  functions whose names happen to match; name fixture functions with the filter in mind.
- **JSON key metavariables keep their quotes.** `"$KEY": "$CMD"` binds `$KEY` as `"apiKeyHelper"`,
  so the key regex is `^"(apiKeyHelper|...)"$`. A Windows path arrives with doubled
  backslashes in JSON text (separator `(?:/|\\\\)`) and single ones in plain YAML.
- **JSON keys and values can hide behind `\uXXXX` escapes.** For a dotted setting name, match
  each dot-separated part by its decoded length, plus a lookahead that requires an escape
  somewhere in the string; one total length is too loose (an escaped
  `files.readonlyFromPermissions` has the same 29 characters as
  `chat.tools.global.autoApprove`). For a free-form key (a command allowlist entry), flag any
  escape of a printable ASCII character except `& ' < = >` (Go and Gson write those), `"` and
  `\` (they have short escapes), and `\\u` (an escaped backslash). See
  `vscode-chat-auto-approve`.
- **JSON rules:** match key-value pairs, not whole objects, or the finding lands on the
  object's first line. Scope with `pattern-inside: '"permissions": {...}'` and then
  `pattern-inside: '"allow": [...]'`, and match the value with `pattern: '"$X"'` plus
  `metavariable-regex`.
  When the object's shape is the signal (a plugin monitor is `{name, command, description}`),
  match the whole object with `{..., "command": "$CMD", ...}` and add `focus-metavariable: $CMD`
  so the finding lands on that key's line.
  A bare `'"$V"'` matches object keys as well as values, and its range includes the quotes
  while `"$K": "$V"` focused on `$V` doesn't; put one `focus-metavariable: $V` over all
  branches so a value several branches match gives a single finding. For the entries of a
  named array, `pattern-inside: '"allowed": [...]'` plus `'"$V"'` also matches the key
  itself; use `pattern: '"allowed": [..., "$V", ...]'` with `focus-metavariable: $V`.
- **YAML rules:** `pattern: $V` binds every node, whole mappings included, so a one-line
  mapping (`K: v`) gives a second finding with a different range. Guard with a scalar-only
  `metavariable-regex`.
  A plain `~` is YAML null, not a string, so a home-path check must require quotes around a
  bare tilde.
- **`metavariable-regex` is anchored at the start** of the value, like Python's `re.match`.
  Prefix `.*` to find something mid-string. A name test such as `(?:^|[._])retriever$` therefore
  never matches `self.retriever`; write `^(?:[\w.]*[._])?retriever$`. A JSON string value keeps
  its escapes, so an embedded quote arrives as `\"`: allow `\\?` before quote characters. A path
  separator written `\\{1,2}` eats the backslash of an escaped quote; use `\\{1,2}+(?!["'])`.
  When a path regex reads file names out of a shell line, keep whitespace out of the name
  segment, or prose ("copy it to ~/.mcp.json and run setup.ps1") reads as one file name. Put
  alternatives in one regex with `|`, because `pattern-either` can't hold bare
  `metavariable-regex` entries. To tie a value test to one of several key names, give each
  `pattern-either` branch its own nested `patterns:` (`pattern: '$E: $V'` plus its
  `metavariable-regex` pair); `metavariable-pattern` needs the same nesting. A word-boundary
  test followed by an end-of-entry lookahead (a
  verb inside `close_ticket"`) must consume the rest of the name first (`[^\s,"']*+`), or it
  fails.
- **Long regexes can be commented.** OpenGrep's regex engine is PCRE: `(?x)` verbose mode
  (whitespace ignored, `#` starts a comment, so write `\s` and `\#`), backreferences and named
  groups (`(?<file>...)` then `\k<file>`), and `(?(DEFINE)(?<name>...))` with `(?&name)` to
  reuse a piece all work. In `(?x)` mode whitespace inside `[...]` is still literal (unless
  `(?xx)`), so a character class wrapped across lines silently matches spaces and newlines:
  keep classes on one line. A possessive run whose class includes the character that must come
  next eats it and never matches (`[*/ ]*+\*`); use a plain or lazy quantifier there. A
  whole-file gate that uses `^` needs `(?sm)`, not `(?s)`. A subroutine call to a one-character group works inside a
  lookbehind (`(?<!(?&hidden))`), so a class can be defined once and reused. A
  `(?(DEFINE)...)` placed before a top-level alternation serves every branch. Never put a
  capturing group in a `metavariable-regex`: it adds a hidden `$1` to the finding, and
  OpenGrep can then report the same finding twice; write `(?:...)`. YAML anchors (`&x` / `*x`) do not: the rule fails to parse. To share
  one regex between two shapes, bind the same metavariable in both branches of a
  `pattern-either` and put one `metavariable-regex` after it.
  Inside `(?(DEFINE)...)`, anything outside a named group never runs and nothing warns: a
  trailing `(?::tag)?` written after `(?<image>...)` closed is silently dropped, so wrap the
  whole definition in the group. Branch reset `(?|A(?<X>...)|B(?<X>...))` works, so one regex
  can replace several `pattern-either` branches that each bind the focus metavariable; merging
  three branches this way cut one rule's CPU time by about two thirds.
- **JSON mode only scans known extensions.** OpenGrep's JSON parser handles JSONC content
  (comments, trailing commas) in `.json` files, but it skips other extensions, `.jsonc` and
  `*.code-workspace` included, even when `paths.include` names them. JSON patterns also ignore
  key order, so a config where the last matching key wins (opencode and Kilo `permission`
  maps) needs a regex rule too. For those, write the rule with `languages: [regex]`, which scans any file, and skip
  line comments with `(?m)^[ \t]*+(?!//)` (possessive, so the indent can't backtrack past the
  check) rather than rejecting any `//` earlier on the line, so a URL in a string on the same
  line still matches. A balanced JSONC object can be matched with PCRE recursion,
  `(?<G>\{(?:[^{}"/]++|"(?:[^"\\]|\\.)*+"|//[^\n]*+|/\*(?s:.*?)\*/|/|(?&G))*+\})`
  (exclude only the group's own brackets from the plain class), but run every key lookup
  through a comment-aware line walker too, or a commented-out `// "command": ...` line inside a
  live server matches. A `metavariable-pattern` on a metavariable bound inside nested
  `metavariable-pattern`s errors ("not in scope") when a match bound nothing; put a cheap
  `metavariable-regex` (`(?s).`) on it first.
- **Cap any regex scan that runs to the end of the file.** A lookahead that scans the rest of
  the file (to tell whether a match sits inside a `/* */` comment) hits PCRE's match limit on
  files of a few hundred KB, and OpenGrep then silently drops every finding in that file, so
  padding hides a finding. Cap the scan and make reaching the cap keep the finding. PCRE
  compiles `{0,n}` by copying the group, so a group of a few alternatives fails to compile past
  about `{0,300}`; for a longer reach, define a capped group in `(?(DEFINE)...)` and repeat
  the subroutine call (`(?&run){16}+`). See `vscode-task-runs-automatically`.
  Long single lines fail the same way: a per-character lazy walk
  (`(?: (?&q) | [^\n...] )*?`) hits the match limit on a line of about 25–50 KB. Make each
  step atomic and word-sized, `(?> (?&q) | [^\s...]++ | [^\n...] )*?`, guarded so a word run
  stops before `then` / `do` / `else`. See `mcp-server-bind-all-interfaces-config`.
  Every position where a branch must start has to be a run boundary: keep `{`, `(` and the
  backtick out of the word class, guard `if` / `while` / `until` too, and give a branch whose
  target can sit mid-run (`export COPILOT_ALLOW_ALL=1`) its own walk that stops before it.
  See `ai-cli-bypass-flag-invocation`. A shell command test needs the walk to read quoted
  strings whole (plain, single-quoted, and JSON-escaped `\"...\"`), so a `&` or `|` inside a
  quoted URL isn't read as an operator; an unquoted `&` really ends the command (the shell
  backgrounds it), so don't follow a pipe past one. See `agent-hook-remote-exec`.
  The same limit hits a `pattern-not-regex` used as "the file contains X": one alternation
  over the whole file (`(?s)\A(?=.*?(A|B|...)).*`) fails at about 70 to 140 KB and silently
  keeps the finding. Write one `pattern-not-regex` per literal; a single-literal lookahead
  holds up to about 565 KB. When the signal is "the file has auth", match code shapes
  (`.use(` with an auth name, a header check), not words, or a comment like "no auth here"
  suppresses the finding. That includes a fixture's own `// ruleid:` line inside an
  `app.use(...)` call, so keep annotations outside it, and exempt the SDK's own no-auth names
  (`.noAuthentication`, `new UnauthenticatedUser`). In Python, `(?sm)\A(?=.*?^[^#\n]*?TOKEN).*`
  skips `#` comment lines and holds to about 420 KB. Settings that only describe auth to a
  client (an A2A agent card's `securitySchemes`) are not protection.
- **Check in each client's source whether a config key is live.** The same key can be honored
  by one client and silently ignored by another (`alwaysAllow` / `autoApprove` in Cline and
  Kilo v7, `trust` in a Gemini extension), and a documented connection allowlist (Gemini
  `mcp.allowed`) can turn out to approve tools. Allow-rule syntax differs as well: Claude Code
  reads `:` literally except as a trailing `:*`, so `Bash(curl:*host*)` matches nothing and
  must stay quiet, while opencode and Kilo let a later `"*"` key override earlier entries.
  When the same text means different things in different clients' files (`OPENAI_BASE_URL`
  counts in Qwen Code's settings `env` but not in Claude Code's; Gemini CLI expands `$HOME` in
  MCP args and Claude Desktop doesn't), give each client group its own rule, since `paths` is
  set per rule.
- **Check config and path rules against real public files before choosing confidence.**
  GitHub code search (`gh api search/code` with the text-match header, read as text only)
  found false positives (`~/.ai-dev-kit/.venv/bin/python`, Doom Emacs's `~/.emacs.d/.local`)
  that no invented fixture had. Save samples with `json.dumps(..., ensure_ascii=False)`:
  `\u2014`-style escapes break `\b` next to them and hide matches.
- **Path filters are not tested.** `opengrep test` ignores `paths.include`, so verify filters
  with a quick `opengrep scan` on a throwaway directory as well. A bare filename in
  `paths.include` (`mcp.json`) matches at any depth. `opengrep scan` with explicit file targets
  still applies `paths.include`, so copy a fixture to a real path (`sub/CLAUDE.md`) to scan it.
  Paths can't be pinned to the repository root: a leading `/` (`/.mcp.json`) still matches at
  any depth, and an `exclude` of `*/.mcp.json` is read relative to the scan target, so it drops
  the root file when someone scans from a parent folder. Exclude known nested layouts by name
  (`plugins/*/.mcp.json`) instead. Globs accept character classes (`[Pp][Rr][Ee]…` for a
  client that matches file names in any case) but not brace lists (`*.{sh,py}` matches
  nothing). Several `-f` flags in one `opengrep scan` check several rules' filters at once.
  A rule whose `paths.include` takes `*.yaml` also scans every testbed's `expectations.yaml`,
  so a `line_contains` anchor that quotes the whole matched text becomes an UNEXPECTED finding
  there; anchor on part of the line that the rule doesn't match. An anchor also covers a
  finding on any other line of the file with the same text, so give each near-miss text of its
  own (a quiet server's `"command": "tsx"` next to a reported `"command": "node"`), or a false
  positive there passes unnoticed.
- **Rules that scan the same files share one list.** `build.py` fails when the rules in a
  `SHARED_PATHS` group have different `paths`, and the MCP config families import their path
  lists from one generator (`scripts/gen_mcp_unpinned.py`). Add a new rule to the group or
  import the constants; never hand-copy a path list. Regex rules that share named groups (the
  agent-CLI command-position block) mark them with `# --- <name> (begin)` / `(end)` comments
  and list the rules in `SHARED_REGEX`; `build.py` fails when the copies differ, including
  copies inside nested `metavariable-regex` blocks. Taint rules that share sources, sinks, or
  sanitizers (each MCP tool rule and its agent-framework twin) list the shared slice in
  `SHARED_BLOCKS`; when one rule wraps the shared list in an extra branch, give that rule its
  own path (`{"rule-a": ("pattern-either", 0, "patterns"), "rule-b": ("patterns",)}`). A
  one-rule `SHARED_REGEX` group keeps two copies inside one rule identical. Block-scalar regexes are compared dedented, so copies at different YAML
  indents (or inside a `(?(DEFINE)...)` block, with the markers at the scalar's base indent)
  still count as equal. A rule whose sources are shared as a whole list can't add a source of
  its own (a labeled "safe statement object"): exclude such values at the sink instead
  (`pattern-not-inside: $Q = <... builder(...) ...>`). Secret-name and credential-format regexes live in one generator
  (`scripts/gen_mcp_plaintext_secret.py`), which `gen_secret_in_system_prompt.py` builds on.
  In a generator, build the whole regex string before replacing placeholders:
  `A + B + C.replace(...)` replaces only in `C`, and OpenGrep then rejects the rule with
  "reference to non-existent subpattern". A scaffold string that goes through `.format()`
  needs `{{ }}` for literal braces, comments included.
- **Padding tests must stay under 1 MB.** OpenGrep skips larger files (`--max-target-bytes`)
  without an error in its JSON output, so a padding test above that size proves nothing.
- **Moving the finding inside a regex match.** `\K` moves the finding's start to the part you
  care about (the `"approvals"` member of a multi-line object). A named group in a
  `metavariable-regex` (`(?<PKG>...)`) becomes a metavariable, so `focus-metavariable: $PKG`
  puts the finding on the captured text. Never reuse a group name with `(?J)`: OpenGrep errors
  on the file ("Pcre2.get_offset_start: illegal offset") and drops its findings; validate each
  branch with a lookahead and capture once. A conditional on a named group (`(?(<name>)…)`)
  works where a duplicate name doesn't. Wrap an optional prefix word that would otherwise
  be re-read as the next positional (`"run"`, `"exec"`) in an atomic group `(?>(...)?)`.
  `opengrep test` doesn't accept an annotation on the same line as the code, and a comment
  can't sit inside a `\`-continued shell command, so put `\K` at the program to land the
  finding on the command's first line and annotate above it.
- **Files whose whole content runs** (a hook script named after its event, a plugin module):
  use `languages: [regex]` with the exact names in `paths.include` (regex rules also scan
  files with no extension) and land the finding on the first line of code:
  `\A(?:blank line|#(?!!) comment|// comment|/* */|<# #>)*+\K\S[^\n]*`. The `ruleid:` comment
  above it is skipped as a comment, and a file that is all comments is the `ok` case.
- **Prose rules over config strings** (instructions a classifier reads): scan one sentence at
  a time, and skip a term when a negation or scope word ("read-only", "do not") comes earlier
  in the same sentence. Treat `)` and "but" as clause breaks, or a parenthetical "(never X)"
  hides the rest of the sentence. Review words ("without asking", "don't block") widen
  approval rather than narrow it, and in real files they're everywhere, so the scope named is
  the signal, not the phrase. Make short command names case-sensitive (`(?-i:nc)`), or "NC"
  in prose matches.
- **Regex rules over code and markup.** Let a key match skip comments between keys
  (`[{,](?:\s++|//[^\n]*+|/\*(?s:.*?)\*/|<!--(?s:.*?)-->)*+`), since a commented-out line
  between object keys is common. HTML fixtures for regex rules accept `//` annotations inside
  `<script>` blocks.
- **A lazy scan from an outer key reports one finding per object.** It stops at the first
  qualifying member, so write fixtures with one positive per object. To report each member
  instead, intersect the object's range with an entry regex that restarts where the last match
  ended: `(?:^|\G)…\K`.
- **Front matter checks.** To require something at the top of the file, don't run one regex
  from `\A` to the target: it hits the match limit on large files. Use `patterns:` with two
  `pattern-regex` entries, `\A<header>(?s:.*)` and the local target. A byte-order mark is
  `\x{FEFF}` (regexes run in UTF mode), not `\xEF\xBB\xBF`. OpenGrep keeps a leading BOM in
  the text it scans, so a mid-file BOM is `(?<!\A)\x{FEFF}`. Characters above U+FFFF work as
  `\x{E0041}`. Inside a `>-` folded scalar, a
  `(?x)` `#` comment at the base indentation swallows the rest of the regex, because YAML folds
  those lines into one; put comments in YAML comment lines outside the scalar.
  "Front matter without key X", where X may come before or after the target key, is the range
  `\A---[ \t]*\r?\n(?:(?!X[ \t]*:|---[ \t]*\r?\n)[^\n]*+\n)*+---`, intersected with the
  target line: the possessive line loop stops at a column-0 X wherever it sits.
- **Nesting regex ranges.** Several `pattern-regex` entries in one `patterns` intersect, so
  "front matter, then a `hooks:` block, then a `command:` line" works as three ranges. Named
  groups in a `pattern-regex` become metavariables an outer `metavariable-regex` can test.
  Don't capture inside a lookahead on a range that nests: the binding comes from the outermost
  match. Match from the key line instead and reuse pieces with `(?(DEFINE)...)` subroutines.
  Many ranges intersected in one rule get slow on large files even when each regex is fast:
  anchor each branch's own regex at the region's start instead of intersecting it with a
  shared range (one front-matter rule went from 20–48 seconds to about one on a 50 KB file).
  In `.md` front matter fixtures, YAML `#` comments work as `ruleid:` / `ok:` annotations when
  each sits directly above the flagged line.
- **YAML checks inside Markdown front matter.** `languages: [regex]` rejects any `pattern`
  clause, even inside a `metavariable-pattern` with another language. Use
  `languages: [generic]`: bound the region with `pattern-regex`, then run YAML patterns on it
  with `metavariable-pattern` and `language: yaml`, and findings land on the right lines. Bound
  only the key's own block (`mcpServers:`), not the whole front matter: a `: ` in a
  description makes the YAML parse fail silently, with no findings, and the parse error also
  drops every other rule's findings on that file. A nested
  `metavariable-pattern` with no `language` reuses the parsed subtree; adding `language: yaml`
  re-parses the bound text, which silently fails on an indented fragment. Block regexes must
  also continue over column-0 `#` comment lines, or a comment between list items ends the
  block. `subagent_patterns()` in `scripts/gen_mcp_unpinned.py` does all of this for the MCP
  config families.
- **Several fixtures per rule.** `opengrep test` treats every `<rule-id>.*` file as a fixture,
  so cases that need their own file (front matter) can each have one. `build.py` requires
  `ruleid:` and `ok:` cases across the set, not in every file.
  Name them `<rule-id>.<tag>.<ext>` (`x.stdio.env`); `<rule-id>-stdio.env` is not picked up.
  `opengrep test` doesn't read `REM` or `::` annotations in `.cmd` fixtures; use `#` lines. In
  `.razor` and `.cshtml` fixtures use `<!-- ruleid: ... -->`; `@* *@` comments are rejected. To
  test one rule's fixtures, run `opengrep test <its folder>`: `opengrep test --config <rule
  file> <dir>` fails with "the config must be a local directory" (OpenGrep 1.30.2).
- **Path globs match directories too.** `paths.exclude: "*docker*"` matches any path segment,
  including the scan root given on the command line, so `opengrep scan mydocker-proj` drops
  everything; `*docker*.sh` matches only file names. `opengrep test` ignores `paths`, so check
  path filters with a real scan.
  `app/**/admin/**` excludes nested Next.js admin routes (`src/app/...`, `apps/web/app/...`)
  without dropping a scan root that is itself named `admin`; `*/admin/*.py` does the same for
  Python.
  `*` also matches dot folders: `*/hooks/hooks.json` picks up `.github/hooks/hooks.json`, so
  check which other clients' files a glob reaches, and exclude them by name.
  `*.continuerc.json` doesn't match a bare `.continuerc.json`; list both. A plain `.env`
  entry matches `.gemini/.env` at any depth but not `.env.example`.
- **Compose files.** In a YAML rule, `pattern-inside` of `$SVC:` / `...` / `ports: [..., $P,
  ...]` / `...` binds per service, and a long-syntax ports entry binds `$P` to its raw mapping
  text. `command: $C` binds a block list as raw text including the `- ` markers, so one regex
  covers string, folded, flow and block forms. OpenGrep resolves an alias (`environment:
  *env`), but the resolved node keeps the anchor's line numbers, outside the service, so
  service-scoped patterns drop it; match the alias or merge key at the service and run a regex
  over the anchor's text. A test for "this service is an MCP server" by name needs a stand-down
  for host-monitoring images (node-exporter, cAdvisor): their `container_name` often carries
  the project's prefix, and they mount `/` on purpose.
- **`metavariable-pattern` scope.** It matches anywhere inside the bound text, not the whole of
  it: when `$LOAD` is `open(hf_hub_download(...)).read`, a pattern for `hf_hub_download` still
  matches, so force a bare dotted name first with `metavariable-regex: ^[\w.]+$`. It resolves
  import aliases. A metavariable bound inside it only reaches conditions inside that same
  `metavariable-pattern` (a sibling `metavariable-regex` silently matches nothing), although
  `focus-metavariable` still reaches it. With `language: regex` it produces one finding per
  inner match, which splits a table into its entries; when nested inside a table-level
  `pattern-regex` it leaves the finding on the table's first line, so capture a named group in
  the inner regex and `focus-metavariable` on it. Over a JSON array metavariable
  (`"args": $ARGS`) a `language: regex` pattern matches nothing, not even a literal; use
  `metavariable-regex` on `$ARGS` instead.
- **`pattern-not-inside` is checked against the whole match, before `focus-metavariable`
  narrows it.** When the flag sits in a call's argument array, `[..., "--sandbox", ...]` doesn't
  exclude it; add a `$F(..., [..., "--sandbox", ...], ...)` twin.
  `pattern-not-regex` works the same way, which is useful: `\bmax_execution_time\s*=\s*(?!None\b)`
  says "this call also sets a time limit" while the finding still lands on the focused value.
  A `pattern-not-inside: $LOG.$LVL(...)` with no regex on the names excludes every method call
  (`subprocess.Popen(...)` included) and silently removes findings.
  The same goes for an object inside a call: `pattern-not-inside: {..., allowedTools: $A}`
  can't exclude a match whose range is the whole `hostedMcpTool({...})` call. Match the options
  object (`pattern-inside: hostedMcpTool($OPTS)` plus `pattern: '{..., serverLabel: $L, ...}'`)
  so object-level `pattern-not`s apply. `metavariable-pattern: '"never"'` over a value also
  matches a `"never"` key inside a nested filter object; add `metavariable-regex: ^[^{\[]` first.
- **Named lists.** A branch that finds an allow list kept in a constant should accept the
  names teams actually use (`ALLOWED_TOOLS`, `TRIAGE_TOOLS`) and skip deny-style names
  (`DISALLOWED_*`, `RISKY_*`). When a sibling rule owns the same list in some files (a `-cli`
  twin for lists passed to an agent CLI), have this rule stand down there with a whole-file
  `pattern-not-regex` on the sibling's marker (`(?s)\A(?=.*?--allowedTools).*`).
- **Report each value once.** When a value could be reported both where it's assigned and
  where it's used, give both branches the same name regex: one reports at the assignment, the
  other skips uses of a name that regex matches. To skip a guard name
  (`BLOCKED_FLAGS = [...]`), give `pattern-not-inside` a nested `patterns:` block:
  `pattern-inside: $NAME = $V` plus a `metavariable-regex` on `$NAME` (OpenGrep 1.30.2; an
  earlier note here said this wasn't possible).
  A second positive pattern in the same `patterns` can keep a nested match, so
  `$C(..., host=$H)` inside `uvicorn.run(app_factory(host=...), ...)` comes out as a second
  finding; guard it with `pattern-not-inside: outer(..., $C(..., host=$H, ...), ...)`.
- **"Another key is the client's too."** To clear a finding when a sibling value in the same
  options object is also request data (a client-sent `tools` list next to its `messages`), use a
  sanitizer, not a sink condition: `pattern-inside: '{..., tools: $T, ...}'`, the conditions on
  `$T`, then `pattern-inside: '{..., $K: $M, ...}'` and `focus-metavariable: $M`. Sanitizing the
  value clears the options object, so sinks that pass the object itself go quiet too.
  Sanitizers run over every object in the file, so keep their conditions cheap: two-field
  destructuring regions (`const {..., $A, ..., $B, ...} = $E; ...`) and deep sibling checks
  (`{..., $K: <... $O.$F ...>, ...}`) made this rule time out on large files. Test "is request
  data" with a `metavariable-regex` on the bound expression (`$E`, `$O`) instead.
  `pattern-not-inside` also unifies with metavariables bound earlier in the same `patterns`
  (OpenGrep 1.30.2). A destructuring pattern `const {..., $T, ...} = $E` matches only shorthand
  fields; a renamed one (`tools: picked`) needs `{..., $F: $T, ...}`.
- **"Starts with" checks.** `metavariable-comparison` with a pattern built at run time
  (`re.match("^" + str($F), str($V))`) silently never matches. Anchor the value structurally
  instead: `$F` itself, or `<... $F ...>.$M(...)` for a method call whose receiver contains it
  (`(tools ?? []).map(f)`, `tools.filter(f)`), which leaves out `SERVER_TOOLS.filter(t =>
  enabledTools.includes(t.name))` and `helper(enabledTools)`.
- **File-level gates.** "Report only in a file that also does X" is a whole-file
  `pattern-not-regex: (?sx)\A(?!.*?(?: X1 | X2 )).*` on the sinks it applies to; verbose mode
  keeps the alternatives readable, and Python's `^` needs `(?m)`.
- **Tie a finding to the right call** with `$...ARGS`: `pattern-inside: $P = $DL($...ARGS) ...
  $LOAD($P)` then `pattern: $DL($...ARGS)`. Without it, any other call to the same function in
  the region fires too. Two branches that match the same range give one finding.
  Likewise, after a region `pattern-inside` (a write ... then a run), `pattern: $X` matches
  every use of `$X` in the region, including a later `return { x }`; add a second
  `pattern-inside` on the exact call so the finding stays on it.
- **Constant propagation.** `"=~/regex/"` string patterns and boolean literals (`allow_x=True`)
  also match module constants. So does a string pattern inside `metavariable-pattern`: when
  `$PROG` is `AGENT_BIN` and `AGENT_BIN = "/opt/tools/claude"`, `'"=~/claude$/"'` matches. It
  also finds the literal inside `env.get(..., "x")`, `?? "x"`, and ternaries, so exclude
  comparisons (`pattern-not-inside: $A == $B`). It doesn't carry `const HOST = process.env.X ??
  "0.0.0.0"` into a later `host: HOST` in TypeScript; add a `$HV = $H; ...` branch. f-strings
  and `+` built only from module constants do resolve for a `"=~/.../"` pattern, but keep
  backslash escapes (`\w`, `\/`) out of that regex, which then silently stops matching; use
  classes such as `[^/:]`. An f-string with a run-time part doesn't resolve; match its raw text
  with a `metavariable-regex`, and note that f-string patterns match only exact text
  (`f"pytorch/vision:{$X}"` works, `f"pytorch/...{$X}"` doesn't). A value read from the
  environment into a variable (`t = os.getenv(...)`) isn't propagated: use a `pattern-inside: $T
  = os.getenv(...) ...` region, excluding `$T = $Y ... $T = $Z ...` so a later reassignment
  isn't reported. In YAML rules, `command: $CMD` binds the value with its quotes, so allow
  `["']?`. `"$T"` binds the text of a module or local string constant through constant
  propagation in Python and TypeScript, which is much cheaper than a `$N = "$T" ...` region. A
  `metavariable-pattern` with `language: generic` or `regex` over a bound string literal reports
  its inner bindings one character early (the quote); bind the content with `"$T"`. `"=~/.../"`
  string regexes are unreliable on backslashes in Python raw strings (`!.?\[` misses
  `r"!\[..."`, `!.{0,2}\[` works); test each one.
- **Numeric thresholds.** `metavariable-comparison: $N >= 1000` evaluates more than literals:
  `1_000_000`, `10**6`, `int(1e6)`, `1e6`, module and local constants, and TypeScript `10 ** 6`.
  Inside a `metavariable-pattern`, `pattern: $N` also matches sub-expressions, so
  `cfg.get("k", 5000)` and `x ?? 5000` match too; add a `metavariable-regex` on the whole value
  to skip fallbacks and clamps. Constant propagation evaluates `CONST or 5000` as 5000 when
  `CONST = None`, so a fallback fixture needs a run-time value such as a parameter.
- **TOML fixtures.** Literal strings can't contain `'`, so realistic hook commands use basic
  strings with `\"` escapes. A `[hooks]` table after `[[hooks.X]]` is invalid TOML: put each
  form in its own fixture and check every fixture with `tomllib`.
- **"Has no X" tests over mixed shapes.** A test for "an entry with no matcher" that must cover
  flat entries and nested groups needs one branch per shape; otherwise the top-level file
  object passes as "an object with no matcher" and every finding gets through.
- **Keywords that mean different things on save and load** (`weights_only`, `allow_pickle`):
  exclude save-side callees with `regex: ^(?!.*(?i:save|dump|export|write)\w*$)` on the
  function name.
- **Taint through an output parameter.** A source with `by-side-effect: true` and
  `focus-metavariable: $DST` taints the variable after the call
  (`download_url_to_file(url, dst)`). `opengrep test` runs in default mode only, so cover a case
  that needs cross-function taint in a testbed with `requires: taint-intrafile`. When a search
  rule and a taint rule cover one risk, exclude the
  search rule's matches from the taint sources so each issue is reported once.
- **Python string bindings.** A docstring bound through `"$D"` comes without quotes, but a
  keyword argument bound as `$D` keeps them, and any `f` / `r` prefix. A "preceded by a quote"
  check must exempt the literal's own opening quote (`(?<!\A['"])`). A `metavariable-regex` on
  raw text covers `"a" + "b"`, implicit concatenation, `"".join([...])`, and helper calls
  without extra patterns. A `pattern-regex` combined with `pattern-inside: '"$S"'` finds text
  only inside strings and lands on the matched line. `Annotated[$T, $D]` also binds `$D` to
  `Field(...)`; require a string with `^[rRuU]?["']`. Python 3.14 t-strings don't parse in
  OpenGrep 1.30.2. A docstring's `"$D"` value has `\\` and `\n` processed but `\u`, `\U`, `\x`,
  and `\N{...}` left as written (keyword arguments keep the raw source text), and a raw
  docstring is bound twice, with and without its quotes; `r"$X"` is a valid pattern that matches
  only raw strings. Python `$X = $E ...` regions don't extend past the end of a `with` block, so
  add `with` variants. They do reach into later function bodies, decorated ones included. A
  `$P = $HEAD(...) ... $P(...)` region covers every statement in between, so `pattern:
  $HEAD(...)` also matches a neighbouring `partial(...)` assigned there; bind the right-hand
  side (`$P = $PV ... $P(...)`) and use `pattern: $PV`. `import fastmcp` as a region step also
  matches `from fastmcp import X  # noqa: E402`, so "set before the import" is a plain region

  any order (`f(..., args=$X, ..., shell=True, ...)` also matches `shell=True` first), and
  `$KW=[...]` binds any keyword name. A slice (`text[:6000]`) drops taint and propagators
  don't restore it; add
  slices of visibly tainted values as sources. In an f-string, `'"$S"'` binds each literal
  fragment separately, so text that spans an interpolation needs a line regex (skip `#`
  comments; allow `(?:\b[fFrR])?` before the quote, since a bare `\b` before a quote fails).
  `{..., $K: $V, ...}` doesn't match a dict that also unpacks another (`{**os.environ, "K": v}`);
  add `{..., **$BASE, ..., $K: $V, ...}`. Settings kept in a dict of defaults (applied in a
  loop or passed as a child process's `env`) are invisible to an `os.environ[$K] = $V`
  pattern; match the dict entry and focus on its value. `metavariable-comparison` checks
  key/value pairs in one condition:
  `(str($K) == "NAME" and re.match("(?i)(a|b)$", str($V))) or ...`.
- **Python pattern shapes.** `(...)` matches any parenthesized expression; a tuple needs commas
  (`(..., $A, ...)`). `[$...X]` doesn't bind inside list literals. A dict with a `**`
  unpacking (`**os.environ` first, `**base` later) needs its own `{**$E, ..., "K": $V, ...}`
  pattern, which covers both positions. A function-body pattern
  with one statement matches only that exact body: to match "logs, then always allows", use
  `...` then `return Allow(...)` and exclude `if`, `raise`, and `<... Deny(...) ...>`.
  `def $F(..., $P, ...)` matches typed and defaulted parameters too, and `$P = $D` also matches
  `$P: T = d`; exclude the typed form explicitly when it matters.
  Dict patterns ignore key order, and `{...}` also matches comprehensions. To tell which entry
  comes last (a trailing `**body` that overrides a server-set key), run a regex over the
  literal's text: start the first entry with `(?<=^\{)`, since `(?:^\{|,)` never matches it,
  and balance brackets in value regexes so `**body.get("filters", {})` stays one entry.
  `$A | {...}` also matches `{...} | $A`; read the order from the text as well. A class-held
  setting (`limit: int | None = None`, read as `self.limit`) needs its own branch: a
  `pattern-inside` of the class with `$ATTR = None`, the call with `self.$ATTR`, and a
  `pattern-not-inside` for a method that assigns `self.$ATTR`.
- **TypeScript pattern shapes.** `'{...} as T'` and `'{...} satisfies T'` match almost any
  expression, so in `pattern-not-inside` they remove every finding; exclude an SDK type by its
  required keys instead (`'{..., description: $D, prompt: $P, ...}'`). `'x' as const` and
  `[...] as string[]` bind `$V` twice (with and without the cast); add
  `pattern-not-inside: $X as $T` inside the `metavariable-pattern`, or use a
  `metavariable-regex` that accepts only the bare form (`process.env as Record<string, string>`). A rule listing
  `[typescript, javascript]` can't use `??` or `satisfies` in a pattern (the JavaScript parser
  rejects both); use the deep operator (`<... "x" ...>`, `const $CFG = <... {..., tools: $T,
  ...} ...>;`). `const $X = ...` also matches `export const`. Object methods
  (`{ k() {...} }`, `{ k: function () {...} }`) don't bind as `k: $T`;
  `{..., k($...P) { $...BODY }, ...}` matches both forms.
  In `const $X: $TYPE = ...`, `$TYPE` binds only a generic's name (`Record`), and type
  patterns ignore type arguments (`Record<$K, AgentDefinition>` matches `Record<string, {...}>`).
  To scope by declared type, read the declaration as text: a `pattern-regex` with a balanced
  object, `(?(DEFINE)(?<obj>\{(?:[^{}]++|(?&obj))*+\}))`, intersected with the object
  pattern. Cover `= {...} satisfies T`, `as T`, and `as const satisfies T` as well as the
  annotation; switching to `satisfies` to keep literal key types is a common cleanup (found
  by the 2026-10-25 batch refactor). Constant propagation still works through a typed const
  (`const M: AgentDefinition["permissionMode"] = "acceptEdits"`).
  A statement ellipsis metavariable (`$...REST`) after an import doesn't reach inside
  `export function` or `export class` bodies; plain `...` does. After `...`, a statement
  pattern `$RUN(...);` also matches the call inside `const x = ...`, `return await ...`, and
  `if` blocks, and `$W(...);` matches `await $W(...);`. A shorthand property `{description}`
  matches `{..., description: $D, ...}` with `$D` bound to the name, and `{..., $F: $V, ...}`
  with both bound to it; exclude shorthand with `metavariable-comparison: str($F) != str($V)`.
  Method patterns match any API with the same method name: `$T.get($K)` also matches
  `collection.get({where: ...})`, so exclude object-literal arguments. Options built before
  the call match with `const $OPTS = {..., filter: $X, ...}; ... $I.$M($OPTS);`. Taint doesn't
  pass into or out of an object literal with a computed key (`sink({[k]: 1})` isn't reported,
  OpenGrep 1.30.2); match such a literal structurally and treat it as a source.
  `$S.put(...)` doesn't match optional chaining (`config.store?.put(...)`); add a `$S?.put(...)`
  branch, which binds `$S` twice (`config.store` and `config.store?.`), so a name regex should
  accept one. `return $E` also matches arrow functions with expression bodies. Function
  expressions (`return async function inner() {...}`) match arrow patterns
  (`async ($...P) => $BODY`), but a function declared inside a factory and returned by name
  (`function inner() {...} return inner;`) needs its own branch. Excluding nested
  callbacks with `$X.$METHOD((...) => {...})` also excludes imported helpers such as LangChain.js
  `tool(async () => ...)`, because imported names resolve to dotted names; name the callback
  methods. A bare `{...}` or `{..., k: $V, ...}` inside a TypeScript `metavariable-pattern`
  parses as a block and never matches an object; test the bound text with `metavariable-regex`
  instead. Shared options spread into a call (`{...DEFAULTS, serverLabel: ...}`) hide the keys
  a "has no X" test looks for: resolve a spread of a `const` object in the same file
  (`const $D = $DOBJ; ...` plus a regex on `$DOBJ`) and stay quiet on other spreads.
- **Java pattern shapes.** A typed metavariable (`(ChatClient $C)`) or `metavariable-type` with

- **C# pattern shapes.** `$T $V = ...` and `$V = ...` don't match `var v = ...`; list

- **Rule syntax traps.** A `pattern-either` branch that holds only conditions fails with "at

  loses its label in TypeScript array callbacks (default mode, and intrafile mode when the
  array is reached through a field); add a propagator from the receiver to the call result. A
  route registration such as `app.get("/x", (req, res) => ...)` must not count as an HTTP
  source: a source covers the whole handler, and OpenGrep then drops every source inside it.
  In Java, taint reaches a lambda body through captured variables, but a fluent chain with a
  lambda anywhere in it (`chatClient.prompt().user(u -> ...).call()`) drops taint in
  `--taint-intrafile` mode. A propagator `pattern: $CALL` plus `$R.$M(..., ($P) -> $B, ...)`
  from `$R` to `$CALL` restores it; add one from `$R` to `$P` to reach the callback's parameter.
- **Taint flows through every call.** A wrapping call such as `int(...)` or `Number(...)` used
  as a sanitizer clears everything inside it, so `float(eval(x))` goes silent: give value
  sanitizers `exact: true`. A client built with a secret taints everything it returns, so
  sanitize constructors, connectors, and HTTP calls with `exact: true`, and `pattern-not` calls
  that are themselves sinks. A lookup with a tainted key (`TABLE[key]`, `TABLE.get(key)`) is
  tainted, so an allowlist table needs its own sanitizer. `for await (const m of query(...))`
  taints `m`. Calling a method with a tainted argument taints the object
  (`repo.index.commit(msg)` taints `repo`), so sanitize the attributes read back from it.
  A comprehension takes its iterable's taint whatever the element expression is, so an
  element-call sanitizer (`[redact(v) for ...]`) needs `exact: true`. Python slices carry no
  taint in OpenGrep 1.30.2: neither `sink(out[:4000])` nor a propagator or sink on the slice
  reports. In TypeScript, once `process.env` is a source
  anywhere in a file, every `process.env.X` read in that file is tainted (it's a global
  l-value), so non-secret reads need a sanitizer; a method call on a tainted TS receiver is
  tainted only when the method is a listed propagator. Propagators don't chain inside one
  expression: `redact(Object.entries(env).filter(...))` needs one propagator that lists every
  function and method shape, with a `$CALL` regex that accepts only a nest of those calls and
  ends in `)`. `pattern: $CALL` plus `metavariable-pattern: {metavariable: $CALL, pattern:
  f($X)}` binds exactly the call, not the calls around it. In `--taint-intrafile` mode,
  module-level taint (`STARTUP_ENV = dict(os.environ)`) is lost inside functions the file never
  calls; add an alias source for upper-case module-level names.
- **Checks before use are side-effect sanitizers.** `by-side-effect: true` models
  `re.fullmatch(p, x)`, `x in ALLOWED`, `x.startswith("-")`. Focus on the checked operand, so a
  blocklist test like `";" in x` doesn't count as safe. `taint_assume_safe_booleans` clears
  `x is not None` but not `bool()`, `len()`, or `.startswith()`. A check on the right of `||`
  doesn't count after the `if`, because OpenGrep treats it as possibly not run. In Python, a
  check on an attribute (`all(... for m in body.messages)`) doesn't clear later reads of
  `body.messages`, since each read is a fresh source; a check on a variable does.
  A value sanitizer (`exact: true`) and a `by-side-effect` sanitizer on the same call don't
  stack: the value sanitizer hides the argument, so `if not is_safe(x): return` stops clearing
  `x`. Use one `by-side-effect: true` sanitizer with `focus-metavariable` on the argument; it
  clears later uses and the call's result. A sanitizer also beats a source on the same
  expression, so a generic `$MAP.$KEY` sanitizer needs a negative lookahead for the names the
  source must keep (secret-named variables). `len()` and `bool()` still carry taint with
  `taint_assume_safe_functions`, and `$F(...)` doesn't match them (OpenGrep treats them as
  operators); write them out. An allowlist is not a prefix test: `k.startswith("GITHUB_")` still
  lets `GITHUB_TOKEN` through, so only exact-name tests and tests that drop secret-named keys
  should clear a filtered collection.
- **Taint labels and sanitizer reach.** Unlabeled sources carry the label `__SOURCE__`, so
  `requires: __SOURCE__ and not X` works. A labeled source needs `exact: true`, or everything
  inside it gets the label; `label:` on a propagator is accepted and ignored; and in
  `--taint-intrafile` mode, labels on a call written inline as an argument are lost. A
  sanitizer on a call also hides any sink inside that call's arguments, so a statement
  builder like `text()` can't be a sanitizer; with `exact: true` the nested sink is reported
  (checked 2026-10-23). A sanitizer matching the sink call itself hides it even with `exact:
  true`. A sanitizer that matches a bare name (a zod field `$FIELD`) clears every variable of
  that name in the file; tie it to its source (`const {$FIELD} = $S.parse(...)`).
  A sanitizer that matches a dict or object literal also hides a sink inside it, and on
  2026-10-24 a broad call sanitizer hid sinks in its arguments even with `exact: true` (the
  vector-filter rules); keep sink calls and options objects out of broad sanitizers. A
  sanitizer that matches any call also matches the route registration around an inline
  handler (`app.post("/x", async (req, res) => {...})`) and clears the whole handler; exclude
  calls that take a function.
  `by-side-effect: only` isn't supported: to report a value once, at the call that builds it,
  use a region sanitizer (`pattern-inside: $V = render(...)` then `...`, plus `pattern: $V`).
  To mark one part of another source's data (the message list inside request data), add a
  labeled source with `requires: __SOURCE__` and have sinks require that label
  (`client-message-roles-with-tools`). The renamed variable in
  `const { messages: history } = ...` can't be a taint source; label the destructured
  expression instead.
- **Catch dangerous text where it's built.** A module that passes a query or command to its
  own helper (`_fetch(f"SELECT ... {order}")`) is a cross-function flow that default mode
  misses. Add a sink for the text itself (an f-string or `+` whose literal part starts like an
  uppercase SQL statement, handed to any call except logging), and leave text assigned to a
  variable to the execute sinks, so each issue is reported once (`llm-output-to-sql`, `-ts`).
  In TypeScript a tagged template (`` pg`...` ``, `` prisma.$queryRaw`...` ``) matches
  `$F(..., $Q, ...)` with the template as `$Q`; exclude it with ``pattern-not-inside: $TAG`...` ``.
- **Taint sources and scan modes.** A bare `$V` source matches where a name is defined
  (parameters, assignment targets, destructured names, imports), not uses deep inside
  templates or calls; pair it with `$O.$F` for attribute reads. With `--taint-intrafile`,
  OpenGrep loses module-level taint inside a function the file never calls, while default mode
  keeps it; treat later uses of the variable as sources (`$G = $RHS ... def $FN(...)`). Since
  `opengrep test` runs default mode only, compare a fixture's findings in intrafile mode with
  a scan.
- **TypeScript and JSX shapes for taint.** JSX children spread over several lines need
  `<$C a={$A}>...{$X}...</$C>`, because whitespace text nodes break `<$C a={$A}>{$X}</$C>`.
  Destructuring defaults (`{ x = "v" }` in parameters or `const`) match no pattern; use a
  `pattern-regex` that requires `{` or `,` right before the name, so a plain `const x = ...`
  doesn't match. `class $C { ... k = $V; ... }` matches typed and untyped class fields.
  Typed metavariables (`($M : UIMessage)`) don't resolve destructured props: match
  `function $F({..., $P, ...}: $TY, ...) {...}` with a regex on `$TY`, and find same-file
  types with `interface $TY { $K: $V }` or `type $TY = $DEF;` then `...` (a type-literal
  pattern containing `...` fails to parse). A tagged template's options object
  (`` execa({cwd: x})`...` ``) can be excluded with a sanitizer scoped to that call, and
  `pattern-regex` plus a template pattern works as a sink on the text of `` $`...` ``.
- **Gate on imports.** `pattern-inside: import {...} from "=~/^@?langchain/"; ...` scopes a
  rule to files that import a package (`import { $..._ }` doesn't parse). JavaScript import resolution doesn't cover
  `node:child_process`, default imports, or `require`, and a bare `$X.exec(...)` also matches
  `RegExp.exec`, so gate sinks on the import with a module-name regex. In Python, `@$S.tool`
  also matches an imported bare `@tool`; bind the decorator and exclude modules with
  `metavariable-pattern` / `pattern-not`. `@$D` binds only bare-name decorators and
  `@$D(..., $A, ...)` only positional arguments; add `@$D(...)` and `@$D(..., $K=$A, ...)` for
  call decorators and keyword arguments (`dependencies=[Depends(require_admin)]`). A Python
  import gate `import a.b` also matches `from a.b.c.d import X`. A `pattern-inside` import
  region can't be combined with a whole-file `pattern-regex`, because the file's range starts
  before the import. `import {...} from "$MOD"` also matches
  `import type {...}`. For JSX, `import {$MD} from "=~/^(?:a|b)$/"` binds one name out of a
  multi-name import, `import {$NAME as $MD}` covers aliases, and
  `$MD = $LAZY(() => import("x"), ...)` covers `next/dynamic` and `React.lazy`. A cheap "this file contains X" gate is a whole-file regex next to the
  pattern: `pattern-regex: (?s)\A(?=.*?\.add_tool\().*`, or, to require an import, a
  possessive `pattern-not-regex` such as `\A(?:(?!LINE)[^\n]*+\n)*+(?!LINE)[^\n]*+\z`, which
  holds on large files where the lazy `.*?` form fails at about 140 KB. Both are much cheaper
  than `import $MOD` / `...` regions, and a region that times out drops every finding the
  rule has for that file. An unconstrained `import {...} from "$MOD"; ...` region binds only
  the file's first import, so a `metavariable-regex` on `$MOD` silently fails when the module
  comes later; use a string regex (`from "=~/.../"`) unless another metavariable ties `$MOD`
  to the call. To accept an object built in the app's own helper module (a Jinja `Environment`
  in `app/templating.py`), let the import gate also accept a named import from a module named
  like one (`from [\w.]*(?i:templat|jinja)\w* import`). A word gate also matches the
  fixture's own `ruleid: <rule-id>` comments, so a gate for `katex` always passes in the
  fixture; gate on a quoted module path (`["'][^"'\n]*katex`) instead. In a line walker,
  `(?![^\n]*+"X")` never matches, because the possessive run eats the quote; use `[^\n]*?`
  inside the lookahead.
- **Registration anywhere in the file.** `function $H(...)` followed by `...` and
  `<... $S.reg(..., $H, ...) ...>` matches a registration later in the file, including inside
  another function body, a list, or an assignment, but it starts a region at every function
  and times out on files of a few thousand lines. Instead, find a handler declared before its
  registration with a regex over the declaration that looks ahead for a named registration
  call naming it, and one declared after it (hoisted, or below a factory function) with a
  region that starts at the named registration call and runs to the end of the block. This
  took the MCP and agent-tool rules from timeouts to 2–8 s on 5,000–13,000-line files
  (2026-10-25). In Python, `def $FN(...): ...` followed by `...` reaches past the function; to
  stay inside the body, add a separate `pattern-inside` without the trailing `...`.
- **Metavariables across nesting.** Conditions inside a nested `patterns` or a `pattern-either`
  branch don't see metavariables bound outside it, so put `metavariable-regex` at the outer
  level or bind the metavariable in each branch. The other way round works: outer conditions
  see metavariables bound inside a `pattern-either` branch, but a `metavariable-regex` or
  `metavariable-comparison` on one that a branch never binds silently drops that branch, so
  keep the condition inside the branch that binds it, or make that branch its own source or
  sink. To compare a value found inside a
  `metavariable-pattern` with an outer one, bind it in a nested `patterns:` there and compare
  outside with `metavariable-comparison` (`str($USE) == str($NAME)`). `metavariable-comparison`
  supports `str($A) in str($B)`, `re.match`, `and`, `or`, and `not`, and is much cheaper than
  extra branches; write its regexes with `[.]` instead of backslashes or double quotes.
  `str()` of a string or template literal gives the unquoted text, so
  `str($BIN) == "process.execPath"` works. In a `>-` scalar, a continuation line indented
  further than the first keeps its newline and fails with "not a Python expression"; keep
  every line at one indent. Inside
  `metavariable-pattern`, `pattern-not: <... x ...>` doesn't remove a deep match, because the
  inner sub-match survives; use a `metavariable-regex`. A bare `pattern: $V` inside
  `metavariable-pattern` crashes on a parenthesized value (`(DIR / "x").write_text(...)`) with
  "Invalid_argument: String.sub" and drops every finding the rule has in that file; use
  `pattern-regex` there. In Python that includes a value wrapped whole in parentheses that holds
  a call or a conditional (`(gr.HTML())`, `(a if c else b)`) once a condition reads the bare
  metavariable, and `NOT_PAREN_RECEIVER` below doesn't skip those; spell the shapes out as
  patterns, or match a metavariable already bound outside (`pattern: $NAME`), instead. A `patterns` block holding only a `metavariable-pattern` is "Invalid
  rule schema"; put a `"=~/.../"` string in the call pattern instead. Two positive patterns in
  one `patterns` block intersect by containment, so `{..., "name": $N, ...}` next to a
  card-shaped object pattern also matches a nested object's `name`; bind `$N` inside the same
  object pattern. `pattern-not-inside` can't stand alone
  as a `pattern-either` branch. `'"$S"'` also matches f-strings and template literals.
  Conditions inside a `metavariable-pattern` do see outer metavariables, so branches that need
  one can go inside one outer `metavariable-pattern`. Named groups from a `metavariable-regex`
  and bindings made inside a `metavariable-pattern` print in messages, but an outer
  `metavariable-regex` or `metavariable-comparison` on them silently drops the match.
  `metavariable-comparison`'s `re.match` needs a literal pattern, and string `+`, `.find`, and
  indexing silently match nothing. `focus-metavariable` can't be a `pattern-either` branch;
  split the branch into its own source or sink.
  The `pattern: $V` crash above is one case of a wider one: when a `metavariable-pattern`'s
  value starts with a parenthesized expression followed by more of the expression, whether a
  call, member, or index (`(a or b).strip()`, `(await r.get(u)).json()`, `(xs as
  string[]).includes(k)`) or an operator (`(m.get(k) ?? 0) === 0`, `(k as string) === "HOME"`,
  also behind extra opening parentheses), and a pattern inside matches from that first
  parenthesis, any condition inside it that reads a metavariable bound there
  (`metavariable-regex`, `-comparison`, a nested `metavariable-pattern`) aborts the file with
  "Invalid_argument: String.sub / Bytes.sub", reported at line 1 with no rule named, and every
  rule in the scan loses its findings in that file. A parenthesis later in the value
  (`f((a ?? b) === c)`, `0 === (a ?? b)`) is safe. The inner match has to happen, so a value the inner patterns
  never match is safe. `language:` on the `metavariable-pattern` avoids it but then nothing
  matches. Put `NOT_PAREN_RECEIVER` (`scripts/gen_mcp_unpinned.py`) in a `metavariable-regex`
  on the same metavariable just before the `metavariable-pattern`, and match the common
  parenthesized form at the top level if it matters (a type-asserted allowlist). When the
  condition only picks among a few names, spell them out as patterns instead (`$E.loose`,
  `$E.Loose` rather than `$E.$M` with a regex on `$M`): with no condition inside, nothing
  crashes and the parenthesized values still match. Conditions at the top level, outside any
  `metavariable-pattern`, are safe.
  `pattern-not-regex` drops a match only when one of its regex matches lies inside the match's
  range, and regex matches don't overlap, so a lazy `.{0,N}?` starting at an earlier element can
  swallow the one you meant and suppress an unrelated finding further on. Keep element-level
  regexes short; a whole-file `(?s)\A(?=.*?X).*` still works.
  Because inner conditions see outer metavariables, a metavariable inside a
  `metavariable-pattern` named like an outer one (`$X`) must match the same text; name inner
  ones apart. Named groups in a `metavariable-regex` become metavariables too, so write
  reusable regex parts with `(?(DEFINE)...)` or no groups.
- **Pattern cost on large source files.** OpenGrep gives each rule 5 seconds per file, and a
  rule that runs out reports nothing for it. One long `pattern-inside` region (an import,
  then a `promisify` line, then the call) is several times slower than separate
  `pattern-inside` conditions that share metavariables. `pattern-not-inside: $APP = $K(...)
  ... $APP.add_middleware(...) ...` is roughly quadratic, while `pattern-not-inside:
  $APP.add_middleware(...) ...` does the same job cheaply. Generic regions such as
  `$S = $CLS(...) ...` (or `const $X = $INIT; ...`) over every assignment are costly too, and
  can turn quadratic: name the SDK classes, or the element shape (`new Set([...])`).
  Spell out method names (`$CUR.execute(...)`, `$CUR.executemany(...)`): `$X.$M(...)` plus a
  name regex matches every call first. `--taint-intrafile` analyses every function that
  contains a sink, AI call or not, at roughly a second per 3,000 lines. Time also grows with
  the number of findings in a file, not its size, so benchmark at a realistic finding density
  as well; `pcre2test -t` times a rule regex on its own (it processes backslash escapes in
  subject lines, so double every `\` in a test string). Measure with `--timeout 0 -j 1` and
  user CPU time: `--time` match numbers leave out most of the cost. Order inside `patterns:`
  matters: put the condition that matches least first. A positive whole-file `pattern-regex`
  gate placed first makes other files cheap; a `pattern-not-regex` gate doesn't. Regions from
  every `def` to a later use, or an unrestricted `$T.$EV(...)`, get slow past about 1,000
  lines: start from the import and name the methods. `import gradio` as a pattern also matches
  every `from gradio.x import ...` line.
  Test with a few thousand lines of realistic code, not just the fixture.
  A list pattern with two free metavariables, `[..., $PROG, ..., $FLAG, ...]`, pairs every
  element with every later one: 50 s on a 400-element argv. Bind one by position
  (`[$PROG, ..., $FLAG, ...]`) or as an inline `"=~/re/"` literal (which also follows
  constants), or find the two in separate passes over the same list. Put cheap
  `metavariable-regex` filters before `metavariable-pattern`: filters run in the order listed.
  `opengrep test` applies no timeout, so a slow rule still passes its fixtures; only the
  testbed scan, with the 5-second default, catches it. See `ai-cli-bypass-flag-invocation-py`.
  When timing a rule on a fixture concatenated many times, count findings in the first copy
  only: repeated TS `const` declarations break constant propagation, so later copies
  under-report (Python keeps it).
  A gate first doesn't help files that pass it: OpenGrep still computes every region there. A
  Python `def $FN(...): ... / ... / call(cb=$FN)` region costs every def times the rest of the
  file (79 s on 38k lines, 2026-10-24); a whole-file `pattern-regex` that the file passes a
  callback by name replaced it. Start regions from the specific shape
  (`$NAME = {..., $K: False, ...}`), not `{...}`.
  A `metavariable-regex` or `metavariable-pattern` on a region's value runs only after the
  regions are matched against every use, so `$G = $RHS ...` checked on `$RHS` is still
  quadratic; put the shape in the region (`$G = <... os.environ[$N] ...> ...`). A region that
  ends at a specific later statement (`A ... def $FN`) makes one range per later match; ending
  it at a bare `...` with a separate positive pattern makes one per start. To leave out uses of
  a local that shadows a module-level name, add a `pattern-not-inside` of a function that
  assigns the same name before the use; it's cheap because each region stays in one function.
- **YAML rules on large files.** A bare `$KEY: $SRC` or `jobs: $JOBS` binding matches every
  mapping in the file, and the cost grows fast enough that a rule times out on an 800-line
  workflow under load and silently drops its findings. Re-bind narrowly (`prompt:`, `run:`, an
  env entry) and use `jobs: $_` when the value isn't needed. `jobs: ... $JOB: $BODY` binds
  every job, so bind the job through its `steps:` key. Test speed by copying a job 10 to 30
  times into one workflow. To skip a guard (`author_association`, a same-repo check), write one
  branch outside any `if:` and one inside an `if:` whose condition regex lacks the guard.
- **YAML fixture and parsing traps.** A folded scalar (`>-`) looks the same as a literal block
  (`|`) in the AST. A bare `true` and a quoted `"true"` are different literals. A plain scalar
  containing `: ` breaks the fixture (check fixtures with `yaml.safe_load`), and a `# ruleid`
  comment inside a `prompt: |` block becomes part of the prompt. In the rule file, a pattern
  containing `{..., k: v, ...}` must be quoted, and a regex containing `'`, `: `, or ending in
  `:` (`::):`) needs a block scalar.
- **git takes `--end-of-options` like `--`.** Treat both as ending option parsing. A sink
  branch `$GIT.$METHOD($ARG, ...)` also binds a whole array literal, so one tainted element
  makes the array the sink and skips element-level guards; exclude `[` and `{` with a
  `metavariable-regex` in that branch. simple-git `log({from, to})` builds `${from}...${to}`,
  so `from` can start an argument.
- **Prefer precision.** A noisy rule gets disabled, and then it catches nothing. When in doubt,
  narrow the rule and lower `confidence` rather than widening the match.
- **Metavariable scope across branches.** A `metavariable-regex`, `metavariable-pattern`, or
  `pattern-not-inside` in a nested branch only sees metavariables bound by a positive pattern
  in that same branch. One bound outside silently drops every finding in the file (or errors
  "not in scope"), so bind the metavariable again in each branch. Inside a
  `metavariable-pattern`, a `pattern:` that reuses an outer name rebinds it instead of matching
  it, and a `metavariable-comparison` there can't see the outer value: bind a new name inside,
  then compare outside with `str($RET) == str($C)`. Give each region its own metavariable
  names. A free callee (`$C(...)`) in a branch also matches calls nested in the arguments, such
  as `os.getenv(...)` inside the call you meant; bind the callee once (`torch.hub.$FN(...)`
  with a name regex) and reuse it.
- **Function bodies.** `async def $F($...P):` followed by `$...BODY` binds a Python body, and
  `function $F($...P) { $...BODY }` a JavaScript one; both `metavariable-regex` and
  `metavariable-pattern` work on the body. An anonymous `function ($...P) {...}` doesn't parse
  as a pattern. "Outside any `if`", plus a statement-level regex that allows only event or
  tool-name `if`s, separates a callback that approves everything from a gated one.
- **YAML mapping patterns.** A pattern with two or more keys matches only mappings with
  exactly those keys; add `...` lines to match a subset. A single-key pattern matches inside
  larger mappings.
- **Long values in a regex.** A lazy `\A(?:...)*?` scan over a long string keeps a backtrack
  frame per step and silently stops matching past about 20 KB. A possessive scan
  (`(?:chunk++ | ... )*+`, skipping ordinary text in negated-class chunks) holds past 400 KB.
  In a `pattern-not-regex`, the match starts after `\K`, and an empty match counts as inside the
  finding's range. A regex that carries shared begin/end markers must sit in a `|-` block, not
  `>-`. In a possessive scan that stops at a pivot, check the lookahead before consuming the
  pivot (`(?!(?&reg))\(` when `reg` starts with `\(`); written the other way round it never
  stops and quietly matches nothing. Before a long alternation of names, step over pivots that
  can't start a match with a one-character lookbehind (`(?<![elnst])\(`, built from the last
  letters of every name), and keep a fixture case for each name.
- **Regexes inside code rules.** Two `pattern-regex` entries can't share a captured value, so
  tie a wrapped value to its source inside one regex (a backreference, `\K`, and a lookahead).
  A regex reports one match per starting point, so several sinks after one source need one
  pattern per position (first, second, third). Regex matches don't overlap: a regex from a
  registration to its handler swallows the registrations in between, and `focus-metavariable`
  on a capture group doesn't recover them. In TypeScript a named group doesn't unify with an AST
  metavariable of the same name; name it apart and compare with
  `metavariable-comparison: str($H) == str($NAMED)`. A callee matched by name in a regex loses
  import resolution, so pair it with a cheap import region (`from $MOD import $NAME ...` plus a
  `metavariable-regex` on `$MOD`). In a taint sink, a `pattern-regex` intersected with other
  patterns drops every finding of that sink, even `(?s)\A.*\z` (the same conjunction works in
  search mode and in sources); a regex as its own `pattern-either` alternative of a sink works,
  at about three times its search-mode cost (OpenGrep 1.30.2).
- **Slow regions.** A nested region such as `$O = $E ... $X = <... $O.$F ...> ...` compares
  every pair of statements and gets slow on long files; use two separate regions that share
  the metavariable.
- **Generators can read their siblings.** A generator can take shared pieces (a character
  class between markers, a block of description surfaces) from sibling rule files, check them
  against the parsed YAML, and fail when they drift; keep `SHARED_REGEX` / `SHARED_BLOCKS` as a
  second guard.
  To share a taint source list, export a count computed from the YAML
  (`len(yaml.safe_load(dedent(SOURCES))["pattern-sources"])`) and use it as the `SHARED_BLOCKS`
  stop index, with rule-specific sources after the shared ones. In a generator's non-raw
  `"""` string, regex escapes need doubled backslashes: `\b` silently becomes a backspace and
  the rule fails to load. `yaml.safe_dump` writes `&id` / `*id` aliases for repeated objects,
  which OpenGrep rejects ("Expected a list for pattern-either"); dump with a `Dumper` whose
  `ignore_aliases` returns True. Hand-written anchors and aliases in a rule file fail the same
  way under `opengrep test` ("invalid configuration") although `opengrep scan` accepts them.
  To keep two rules from reporting the same thing, build both from one regex fragment: a
  positive lookahead in one rule, a negative one in the other. When splitting a sibling's regex
  into shared constants, run `build.py --check` before adding the new rules, so you can see that
  the sibling's output is byte-identical.
- **Invisible characters in fixtures.** Agent file-writing tools decode `\uXXXX` in their
  input, so asking one to write `"\u200b"` puts a real zero-width space in the file. Build
  escape text and invisible characters with `chr()` in a script, and check the committed bytes.
- **Default ignores.** OpenGrep skips `dist/` and `vendor/` even with `--no-git-ignore`, so a
  bundled or vendored server there is only scanned when targeted directly. Put testbed bundles
  in another folder (`third_party/`).
- **Test files.** OpenGrep's own ignore list skips only `test/` and `tests/` directories, so
  colocated `*.test.ts` files, `test_*.py` next to the code, and `e2e-tests/` are scanned. A
  rule whose risky shape is one tests build on purpose (an allow-all permission callback, a
  debug switch) takes a `paths.exclude` for them; copy the list from
  `agent-sdk-bypass-permissions(-ts)`. `opengrep test` ignores `paths`, so add a testbed
  near-miss in a test file to prove the exclude. A name that only mentions a test
  (`e2eFixer.ts`) must still be scanned.
- **Bounds checks as sanitizers.** For rules where a number from the request is the risk (a
  token cap, a loop count), a "compared before use" check is cheapest as a `by-side-effect`
  sanitizer on `$L > $R` focused on one side, with a regex keeping the other side a real bound
  (not 0, 1 or None); an `if <... $L > $R ...>:` region is much slower. It clears attribute
  reads (`body.max_tokens`) when the source is the parameter. Deep `<... $L <= $R ...>` does not
  match a Python chained comparison (`1 <= x <= M`); write `$LO <= $L <= $R` as its own
  pattern. A loop's own condition (`for (let i = 0; i < n; i++)`, `while attempts < n:`) is the
  count, not a check: exclude it with `pattern-not-inside` (the `for ($INIT; ...)` form doesn't
  match; spell out `for (let $I = $START; $L < $R; $NEXT) { ... }`). Such rules can't reuse
  every shared request-data piece: `taint_assume_safe_numbers`, `int()` / `Number()`
  sanitizers, and number-typed schema fields clear exactly what they report, so import only
  the allowlist slice and give it its own `SHARED_BLOCKS` group.
- **Callee regexes see the local name.** A `metavariable-regex` on a callee gets the name as
  written, `CrewAgent` for `from crewai import Agent as CrewAgent` (only `metavariable-pattern`
  resolves import aliases), so allow a prefix (`\w*Agent`). `$F(...)` does not match a `new`
  expression: exclusions for constructors need `new Cls(...)` as well as `Cls.$CM(...)`.
- **Name sources also match callees.** A `$O.$F` or `$V` source gated by a name regex matches
  the callee of `self._first_pass(...)` too, and the call's result carries the taint. When a
  name word doubles as an ordinary word (`pass`, `token`), exclude the qualifiers that make it
  one (`first_pass`, `max_tokens`) in the name test itself.
- **Sanitize what builds the client, not just constructors.** A secret handed to a class
  factory (`Memory.from_config(settings)`) is used like one handed to `Memory(...)`; leave out
  prompt and message classes (`ChatPromptTemplate.from_messages`), whose arguments hold sinks
  that an exact sanitizer would hide.
- **YAML value regexes resolve aliases.** In a YAML rule, `image: "=~/regex/"` tests the
  resolved value, so it works through `*alias`; a plain `$IMG` binds the raw text, alias name
  included. Avoid backslashes inside a `"=~/.../"` pattern in YAML double quotes; use `[/]`
  and `[0-9]`. A regex scoped to one YAML document that ends in `(?!---)[^\n]*+` fails at the
  next `---`; make that ending optional.
- **Continued lines in fixtures.** A `ruleid:` comment can't sit above a line that continues a
  `\`-ended line (`else \` then `docker run …`), so cover continued-line cases in a testbed,
  or start a multi-line match at the command line instead of using `\K` at the continued value,
  so the finding lands on a line a comment can mark.
- **Client behaviour lives in odd places.** Read each client's settings migrators for older
  forms it still accepts (Zed converts `"command": {"path": …}` on load); they are easy false
  negatives. A VS Code extension that doesn't declare `capabilities.untrustedWorkspaces` is
  off in untrusted workspaces, so its project config takes effect after Workspace Trust.
- **`await` with type arguments.** OpenGrep 1.30.2 parses `await f<T>(x)` as a call whose
  callee is `await f`, so `f(...)`, `f<$T>(...)`, and import-resolved names all miss it (without
  `await`, `f<T>(x)` matches `f(...)`). Match `$AW($X, ...)` with a `metavariable-pattern` on
  `$AW` (`language: generic`, `pattern: await f` or `await $NS.f`).
- **"The whole value is X" needs a regex.** `metavariable-pattern: os.environ` on a
  `secrets_map=` value also matches `os.environ["ONE_KEY"]` inside a one-entry dict; test the
  whole value with `metavariable-regex`.
- **Taint sinks on library functions.** Generate the dotted callee patterns instead of
  `$FN(...)` plus a callee `metavariable-pattern`, which matches every call first and is slow;
  `pattern-regex` can't gate a sink.
- **One finding per occurrence.** A regex that walks from `\A` to skip earlier text
  (`\A(?:fenced block|other line)*?<target>`) can report only one match per file. Match each
  occurrence on its own with a local test instead: Claude Code's ``!`cmd` `` placeholder is
  `` (?m)(?<=^|[ \t])!`[^`\r\n]+` ``, and that lookbehind also skips a placeholder wrapped in a code
  span and a `` KEY=!`x` `` assignment, which Claude Code leaves as text.
- **Commands embedded in prose.** For shell run from skill or command text, let a danger test
  on the command (shared with the remote-exec rules) carry the precision rather than modelling
  markdown: documentation of the syntax rarely downloads and runs anything. Check per client
  whether a fenced block is inert; clients that read the same syntax differ (opencode runs a
  placeholder glued to the previous word, Claude Code doesn't). A ```` ```! ```` block finding
  lands on the opener line, so put the `ruleid:` comment above the opener: a comment inside
  the block would become a command.
- **Allow lists with deny lists.** Claude Code, Cursor CLI, and Qwen Code check deny (Claude
  Code and Qwen also ask) before allow, so an allow-list rule needs a same-file stand-down for
  a deny or ask entry that covers it; `pattern-not-inside` with `patterns` plus
  `metavariable-regex` works on JSON. A JSONC key regex matches the key at any depth (a
  `"webfetch"` inside `"bash": {}`), so start at the parent key and walk that level.
- **Reading closed binaries.** Claude Code's permission matcher ships only in its native
  binary (about 290 MB); find strings with `grep -b -o` and read around the offset with `dd`,
  since a wide-context grep times out.
- **Testing the tests.** Prove an extra fixture file (`<id>.<tag>.<ext>`) is really tested by
  flipping one annotation and watching it fail. A `--config` list built from a glob of rule
  files must leave out `*.test.yaml` fixtures (opengrep rejects them). When testing a `(?x)`
  regex in Python, join its parts with a real newline: `r"\n"` stays an escape.
- **What a function returns.** `pattern-inside: 'new Agent({..., instructions: $FN, ...})'`
  with `pattern: return $X;` matches every return in the call, a tool's `execute()` included,
  and an arrow callback's expression body counts as a return too. To mean "what this function
  returns", put the return in the function pattern: `($...A) => { $...BODY; return $X; }` is
  the final return only; `($...A) => { ... return $X; ... }` also finds early returns (deep
  `...` reaches into `if` and loop blocks) but enters callbacks as well, so pair it with
  `pattern: return $X;` (which pins the range to the return; without it, `pattern-not-inside`
  tests the whole inside range) and `pattern-not-inside: '$F(..., ($...A) => $B, ...)'`.
  That not-inside also drops returns when the whole agent is built inside a callback (a route
  handler, a `map()`). To test only the function, bind it (`instructions: $FNX`,
  `const $FN = $FNX;`) and match `return $X;` and the not-insides in a `metavariable-pattern`
  on `$FNX`. A declaration's body bound as `{ $...B; }` matches nothing there, and binding the
  whole declaration as a statement `$S` shifted and dropped the rule's other findings (1.30.2).
- **Only the `if` body.** `pattern-inside: if $C: ...` also covers the `else` and every `elif`
  after it (in Python an `elif` is an `if` inside the `else`). To reach only the body, match
  `if $C:` / `...` / `$STMT` / `...` inside a nested `patterns` with `focus-metavariable:
  $STMT`, and put it next to the `pattern:` that picks the expression (see the user-turn
  sanitizer of `llm-markdown-remote-image-render-py`). Likewise, `<... $X ...>` as a statement
  in a `pattern-inside` sequence reaches into expressions only, not into a `with` or `if` body;
  add a `with $CTX:` form for code laid out in Streamlit columns.
- **Bind what a nested negation tests.** In a nested `patterns` (a branch of a
  `pattern-either`), a `pattern-not-inside` or `metavariable-regex` sees only the metavariables
  that branch's own positive pattern binds. Write `pattern: $DG.write(..., $MD, ...)`, not
  `$DG.write(...)`, or `$MD = {...}` matches any earlier dict assignment (OpenGrep 1.30.2).
  Fold such a filter into the `pattern-either` that binds the metavariable instead of adding a
  second `pattern-either` that restates the call: the second one matches every call in the file
  again, which made `llm-markdown-remote-image-render-py` about 20% slower.
- **Field-insensitive siblings.** Taint from a container reaches every value read out of it:
  the index from `enumerate(history)`, the keys from `.items()` on a dict the app built, the
  other slots of a tuple, and every key of a dict a helper returns. Sanitize the ones that
  can't hold model text by shape (the enumerate index, string-literal dict keys, a name already
  divided by a number, numeric format specs, a slot that holds a string literal in every
  tuple of a list literal) or by field name (timestamps, model, error). The keys of a dict
  another function returns can't be told apart this way in `--taint-intrafile` mode.
- **Same-file helpers in default mode.** To treat a call to a generator defined in the file as
  a source, bind its body with `pattern-inside: "def $GEN(...):\n    $...BODY\n..."` and test
  `$...BODY` with `metavariable-pattern`. For a helper defined below its caller, anchor the
  caller as a `def` too (`def $CALLER(...):\n    ...\n...\ndef $GEN`): a bare statement
  metavariable before `...` pairs every statement with every def and timed out on 50 KB files.
  Time a new source on the corpus's largest files before relying on the fixtures.

## Reporting false positives

Open an issue with the rule ID and the smallest code snippet that triggers it. If the code is
from a real project, rewrite it so nothing identifies that project.

## Security issues in this repository

Report privately through GitHub's "Report a vulnerability" on this repository rather than in a
public issue.
